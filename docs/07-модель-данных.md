# Модель данных

Версия 0.2 · 17 ноября 2026 г.

Назначение: сущности, связи и правила сохранности данных для миграций и repositories. Основание: [ТЗ](01-техническое-задание.md) и [API](03-api.md); границы доступа компонентов — в [архитектуре](06-компоненты-и-взаимодействие.md). Это проект модели, SQL-миграции ещё не созданы.

## 1. Сущности и ограничения

| Сущность | Важные поля/ограничения |
| --- | --- |
| users | UUID, нормализованный уникальный login, displayName, timeZone, passwordHash, deletedAt |
| settings | userId, saveNewResults=false, version |
| sessions | hash токена, userId, createdAt, lastSeenAt, absoluteExpiry, reauthUntil, revokedAt |
| api_keys | userId, publicKeyId, hash секрета, mask, createdAt, lastUsedAt, revokedAt; максимум 1 активный |
| telegram_links | userId и числовой telegramUserId уникальны, chatId, confirmedAt |
| recovery_challenges / recovery_codes | Хеш кода/nonce, срок, счётчик попыток, usedAt; привязка к аккаунту и исходному challenge |
| conversion_jobs | userId, source, conversion, status/stage, lease/version, attempts, save snapshot, input key/hash, resultId, errorCode, UTC-времена |
| stored_files | userId, jobId уникален, storage key, безопасное имя, MIME, bytes, checksum, expiresAt/deletedAt |
| quota_reservations | jobId уникален, bytes/slots, expiresAt; изменяется атомарно с задачей |
| idempotency_records | userId/route/key уникальны, request fingerprint, jobId, expiresAt |
| usage counters | userId + UTC bucket + категория; атомарные пределы запусков |
| очередь pg-boss | Собственная схема библиотеки, миграции отдельно от прикладных таблиц |

Файлы не хранить большими бинарными полями PostgreSQL. Миграции версионировать; тестировать обновление и восстановление на отдельной БД. Не копировать работающий каталог БД как «резервную копию»: нужен штатный согласованный backup плюс манифест доступных постоянных файлов.

## 2. Связи и транзакционные правила

- `users` владеет настройками, сессиями, ключами, Telegram-привязками, средствами восстановления, задачами и файлами. Проверенный userId обязателен во всех запросах к персональным данным.
- `settings.userId` уникален; начальное сохранение выключено. Для профиля `users` также нужна версия для If-Match из API; конфликт обновления не затирает данные.
- `conversion_jobs.userId` ссылается на владельца; задача фиксирует снимок сохранения. `stored_files.jobId` и `quota_reservations.jobId` ссылаются на задачу и уникальны. Результат может быть временным: в библиотеку попадают только сохранённые файлы.
- Создание задачи, резерв квоты, запись идемпотентности и enqueue выполняются одной транзакцией. Байты файла сохраняются долговечно до commit, а осиротевшие файлы убирает сборщик.
- Публикация результата проверяет lease/версию, владельца и отмену, заменяет резерв фактическим размером. Старой попытке запрещено публиковать результат.
- Использование recovery code атомарно; максимум один активный API-ключ обеспечивается ограничением БД. Исходные секреты не сохраняются.
- Логическое удаление немедленно закрывает доступ. Физическая очистка и сроки метаданных соответствуют REQ-06/18; каскадное удаление не должно терять задания очистки или журнал удалений для восстановления backup.

Численные квоты и сроки задаёт ТЗ; модель не вводит дополнительные лимиты загружаемых файлов. Время хранится в UTC, размер — целым числом байт.

## 3. Зависимости реализации и проверка

[Каркас TASK-01](tasks/01-каркас.md) создаёт миграции и repositories; [пользователь TASK-02](tasks/02-пользователь.md) реализует учётные записи и восстановление; [конвертация TASK-03](tasks/03-конвертация.md) — задачи, lease и резервы; [кабинет и API TASK-04](tasks/04-кабинет-и-api.md) — библиотеку и доступ по ключу.

До использования миграций проверить связи, уникальность, конкурентные обновления и откат транзакции на отдельной БД. Проверки приёмки: AC-09–11, AC-13–18, AC-20, AC-23, AC-25, AC-27 и AC-29 из [плана](05-план-и-приёмка.md). Изменение полей/связей требует обновления миграций, API-схем, зависимых задач и проверок.

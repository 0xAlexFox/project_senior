# Git-процесс project_senior

## Применение

Перед изменениями и для Git-задач применять `$git-commit` из `~/.agents/skills/git-commit/SKILL.md`. Читать применимые инструкции и этот файл. Изучать связанные разделы навыка по выполняемой операции.

## Ветки и изоляция

Основная целевая ветка — существующая `main`. Ветка `chore/git-setup` и отсутствие `main` относятся к первоначальной инициализации 18 ноября 2026 г.; это историческое состояние, а не инструкция повторно создавать главную ветку.

Для одиночной последовательной работы использовать свою ветку `feature/<тема>`, `fix/<тема>` или `chore/<тема>`. При другом процессе, изменяющем эту папку, или отдельно разрешённых параллельных исполнителях каждому выделять свою ветку и worktree. Защищённые ветки — `main`, `master`, `dev`.

До работы проверить Git root, HEAD, ветку, индекс, чужие изменения и незавершённые операции. Сохранять исходные изменения и staging владельца. Режим, исходную/целевую ветки и рабочую папку записывать в журнал итерации.

## Состав истории

Текущий состав: README, исходная основа, DESIGN.md, спецификации, контракт OpenAPI, проверка документации и история; макет находится в Pixso. Прежний визуальный референс удалён владельцем и не входит в текущий комплект. Из личных заметок отслеживается памятка подготовки нового проекта. Соседние личные заметки и локальные отчёты `.local/` исключены из Git и не должны быть обязательными целями Markdown-ссылок. Краткие результаты итераций сохраняются в `docs/history/`.

Секреты, локальные данные, зависимости, сборки и журналы исключать по `.gitignore` и проверять перед добавлением в индекс. Добавлять конкретные пути/hunks.

## Проверки и коммиты

Проект содержит документацию, контракт API, Python-инструменты и начальный Vue frontend. Для изменений frontend выполнять `npm run check`, `npm run build:web`, `npm run test:e2e` (один worker, установленный Chrome), а также визуальную сверку целевых страниц с Pixso на desktop/mobile и в обеих темах. Для manifests/корневых настроек запускать `npm run check` (документация, дерево зависимостей, форматирование) и `npm run audit:dependencies`; Compose проверять по доступной схеме и, при наличии Docker, `npm run db:config`. Чистая установка — `npm ci --ignore-scripts`; подробности и отложенные runtime-проверки в `docs/project-setup.md`. Для изменения инструмента безопасности запускать `python3 -m unittest discover -s tools/skills/project-security-review/tests -v`. Для документационных изменений запускать `python3 scripts/verify_docs.py`: структура Markdown, переносимые локальные ссылки/якоря, имена файлов, идентификаторы требований/приёмки и внутренние ссылки OpenAPI. Дополнительно проверять смысловую согласованность и diff. Команда должна проходить в копии только отслеживаемых файлов без `.local/`. При изменении OpenAPI дополнительно проверять синтаксис JSON и затронутый контракт. Наличие frontend не подтверждает готовность backend, БД, конвертации или завершение TASK-00–06.

Перед каждым готовым коммитом просмотреть весь `git diff --cached`, выполнить `git diff --cached --check` и `git diff --cached --stat`. После коммита проверить `git show --stat HEAD` и `git status --short --branch`. Ошибка или отсутствие результата обязательной проверки блокируют готовность и интеграцию.

Крупные проверенные блоки сохранять атомарными локальными savepoint-коммитами. Для небольшой неделимой правки достаточно итогового коммита. Журнал — `docs/history/IT-NNNN-<тема>.md`, индекс — `docs/history/README.md`. Использовать первый свободный ID. Заголовок коммита писать по-русски с префиксом `docs:`, `chore:`, `feat:` или `fix:` и ID итерации. В теле указывать причину, изменение, проверку, строки `Iteration:` и `Journal:`. Передавать сообщение через `git commit --file`.

## Проверка безопасности во время разработки

Перед реализацией оценивать чувствительные входы и операции, автоматически применять `$project-security-review` по [обязательным случаям](security-review.md#обязательное-применение-во-время-разработки). Для затронутого чувствительного блока анализ и отрицательные проверки выполняются до готового коммита и итогового отчёта; отдельного запроса владельца ждать не нужно. Это дополняет обязательную проверку всего фактического diff перед merge, а не заменяет её.

## Завершение рабочего сеанса

1. Перед запуском временного сервера, watcher, тестового браузера или другого процесса учесть исходное состояние и сохранить свой идентификатор сеанса/PID и назначение. Ранее существовавший процесс не становится собственным из-за использования в проверке.
2. После завершения проверок и перед итоговым отчётом штатно завершить свои временные процессы и принадлежащие им дочерние процессы, закрыть отдельные тестовые браузеры/контексты, освободить собственные соединения и прочие временные ресурсы. Оставить свой процесс работающим можно только по явному поручению владельца.
3. Проверить фактическое завершение по своим сеансам/PID и освобождение использованных ими портов. Не останавливать пользовательские процессы по совпавшему имени или порту, не применять массовые killall/pkill. Если принадлежность неясна, сначала разобраться; при невозможности безопасного завершения сообщить конкретное препятствие.
4. Удалить только созданные в текущей задаче одноразовые временные файлы. Сохранить оригиналы, финальные артефакты, необходимые скрипты, отчёты и журналы; прежние/непонятные файлы не удалять автоматически.
5. Выполнять этот порядок без рутинных анонсов или обещаний в чате. В журнале достаточно фактического результата; владельцу сообщать при его прямом вопросе, ошибке или необходимом исключении.

## Ревью и интеграция

После проверенного итога представить файлы, результаты, проверки и ограничения, режим, рабочую папку, HEAD и source/target. Задать вопрос о слиянии по режиму изоляции из навыка.

Merge, удаление worktree и создание PR требуют прямого текстового «Да, сливай» на представленный результат и соответствующие действия. Для первой интеграции указать создание отсутствующей `main`. Push, изменение remote, публикация и переписывание общей истории требуют соответствующего отдельного разрешения задачи.

## Безопасность перед слиянием

Перед merge в главную/защищённую ветку применять `$project-security-review` из `~/.agents/skills/project-security-review/SKILL.md`. Выполнить анализ кода и необходимые проверки по [порядку безопасности](security-review.md). После финального коммита сохранить локальный отчёт и квитанцию, перед разрешённым merge выполнить `security_gate.py verify` для точных source/target. Новые коммиты или конфликты требуют актуализации анализа; ошибки обязательных проверок и нерешённые блокирующие находки запрещают интеграцию. Для документации обосновывать неприменимость runtime-контролей, скрипты считать кодом. Это правило Codex; ручной Git и серверная защита веток — отдельный механизм. Проверка не заменяет разрешение владельца.

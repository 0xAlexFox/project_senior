# Git-процесс project_senior

## Применение

Перед изменениями и для Git-задач применять `$git-commit` из `~/.agents/skills/git-commit/SKILL.md`. Читать применимые инструкции и этот файл. Изучать связанные разделы навыка по выполняемой операции.

## Ветки и изоляция

Основная целевая ветка — `main`. При инициализации 18 ноября 2026 г. создана рабочая ветка `chore/git-setup`. Целевая ветка появится при первой интеграции после ревью и разрешения владельца.

Для одиночной последовательной работы использовать свою ветку `feature/<тема>`, `fix/<тема>` или `chore/<тема>`. При другом процессе, изменяющем эту папку, или отдельно разрешённых параллельных исполнителях каждому выделять свою ветку и worktree. Защищённые ветки — `main`, `master`, `dev`.

До работы проверить Git root, HEAD, ветку, индекс, чужие изменения и незавершённые операции. Сохранять исходные изменения и staging владельца. Режим, исходную/целевую ветки и рабочую папку записывать в журнал итерации.

## Состав истории

Исходное состояние проекта включает README, основу, визуальный референс, спецификации и OpenAPI. Из личных заметок отслеживается памятка подготовки нового проекта. Её ссылки на две соседние личные заметки доступны в рабочей папке владельца, эти файлы исключены из Git. Локальные отчёты в `.local/` также исключены, краткие результаты новых итераций сохраняются в `docs/history/`.

Секреты, локальные данные, зависимости, сборки и журналы исключать по `.gitignore` и проверять перед добавлением в индекс. Добавлять конкретные пути/hunks.

## Проверки и коммиты

Сейчас проект содержит документацию и контракт API. Команд сборки приложения и автоматического набора тестов пока нет. Для документационных изменений проверять Markdown-структуру, локальные ссылки, согласованность инструкций и diff. При изменении OpenAPI дополнительно проверять синтаксис JSON и затронутый контракт. С появлением приложения внести сюда его реальные команды проверок.

Перед каждым готовым коммитом просмотреть весь `git diff --cached`, выполнить `git diff --cached --check` и `git diff --cached --stat`. После коммита проверить `git show --stat HEAD` и `git status --short --branch`. Ошибка или отсутствие результата обязательной проверки блокируют готовность и интеграцию.

Крупные проверенные блоки сохранять атомарными локальными savepoint-коммитами. Для небольшой неделимой правки достаточно итогового коммита. Журнал — `docs/history/IT-NNNN-<тема>.md`, индекс — `docs/history/README.md`. Использовать первый свободный ID. Заголовок коммита писать по-русски с префиксом `docs:`, `chore:`, `feat:` или `fix:` и ID итерации. В теле указывать причину, изменение, проверку, строки `Iteration:` и `Journal:`. Передавать сообщение через `git commit --file`.

## Ревью и интеграция

После проверенного итога представить файлы, результаты, проверки и ограничения, режим, рабочую папку, HEAD и source/target. Задать вопрос о слиянии по режиму изоляции из навыка.

Merge, удаление worktree и создание PR требуют прямого текстового «Да, сливай» на представленный результат и соответствующие действия. Для первой интеграции указать создание отсутствующей `main`. Push, изменение remote, публикация и переписывание общей истории требуют соответствующего отдельного разрешения задачи.

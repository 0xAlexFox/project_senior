# Конвертер файлов — проектная документация

Требования: версия 0.2 · Описание макета: версия 1.3 · Актуализация: 20 ноября 2026 г.
Рабочее название: «Конвертер».

Требования подготовлены по [основе](основа.md); оформление будущего продукта описано в [описании макета](docs/mockup-specification.md), адаптированном из предоставленного текстового референса Dimension 19 ноября 2026 г. Это спецификация будущего приложения и обоснование архитектуры. В IT-0017 начат frontend: главная с выбором файла и форма входа на общей базе Vue. Серверные действия пока заменены явными заглушками; backend, БД приложения и реальная конвертация не реализованы. [Подготовка окружения и текущие ограничения](docs/project-setup.md). В Pixso подготовлены 192 кадра: 96 тёмных и 96 светлых. [Состав, проверка и ограничения макета](docs/mockup-specification.md#13-текущий-состав-файла-pixso).

Решения, отсутствовавшие в основе и не согласованные отдельно, остаются предложениями; их реестр находится в документе выбора технологий. В версии 0.2 по согласованной правке удалены ограничения пикселей/длины стороны и внутреннего архива DOCX. Для загрузки сохраняются ограничения формата и размера: JPEG/PNG до 10 MiB, DOCX до 20 MiB. Лимиты результата, квоты хранения и ресурсы обработки задаёт ТЗ.

Для изучения требований достаточно этих Markdown-файлов и JSON. Подготовка зависимостей и доступные команды описаны в инструкции окружения. Дополнительные приложения для чтения и регистрации на сторонних площадках не нужны. В OpenAPI используется вымышленный домен `https://converter.example`; его необходимо заменить при настройке окружения. Реальных ключей, аккаунтов и пользовательских файлов в документации нет.

Исходная `основа.md` сохранена. Прежний визуальный референс удалён владельцем и заменён дизайн-спецификацией нашего продукта. `docs/mockup-specification.md` определяет оформление и подготовку Pixso-макета; `DESIGN.md` служит краткой точкой входа, документ экранов — поведение. Платные тарифы и AI-функции не входят в требования.

Все работы и инструкции задач объединены в [едином плане](docs/work-plan.md): сначала frontend, затем backend и БД, интеграция и подготовка выпуска.

Справочно: [почему не другие frontend-инструменты](docs/frontend-tools-comparison.md) — сравнение альтернатив и SEO для ознакомления.

## Локальный frontend

`npm ci` — установка; `npm run dev:web` — открыть `http://127.0.0.1:5173/`; форма входа — `/auth/login`. Сборка — `npm run build:web`, просмотр сборки — `npm run preview:web` на `http://127.0.0.1:4173/`. Для публикации SPA потребуется fallback на `index.html`; публикация этой итерацией не выполняется.

`npm run setup:python` один раз создаёт локальное окружение Ruff (Python 3.10+; macOS/Linux). `npm run check` проверяет документацию, зависимости, формат и все три линтера; `npm run lint` запускает только ESLint, Stylelint и Ruff, `npm run lint:fix` явно применяет доступные безопасные автоисправления; `npm run test:unit:web` проверяет логику без браузера; `npm run test:e2e` запускает проверки в установленном Google Chrome, одним worker. При отсутствии Chrome установить его либо отдельно подготовить браузер Playwright и изменить channel. Подробности и ограничения — [окружение](docs/project-setup.md) и [статус](docs/project-status.md).

## Зависимости и изменения

Каждый модуль отвечает за свою часть; ссылки используются вместо копирования архитектуры и модели данных в другие инструкции.

| Источник | Ответственность | Что обновлять при изменении |
| --- | --- | --- |
| ТЗ, REQ-01–20 | Продуктовые правила, лимиты, безопасность и сроки | Экраны, API/OpenAPI, архитектуру, модель данных, затронутые задачи и AC |
| Экраны | Страницы, действия и состояния | Описание макета, UI-задачи TASK-02–05 и соответствующие AC; при изменении поведения сначала ТЗ/API |
| Описание макета (`docs/mockup-specification.md`) | Визуальные токены, точные размеры и формулы, компоненты, композиция и структура Pixso | Визуальные указания экранов, TASK-05, кадры Pixso и будущую реализацию UI; поведение сохранять по ТЗ/API |
| API и OpenAPI | Контракты, конфигурация форматов, ошибки | Серверные/клиентские схемы, генератор контракта, TASK-01–05 и проверки примеров |
| Технологии | Выбор инструментов и обоснование | Архитектуру, TASK-00/01/06; менять версии после проверки совместимости |
| Архитектура приложения | Компоненты, изоляция, очередь, расположение кода, зависимости, состав релиза и сервер | Модель данных, API, каркас, инфраструктуру, README, TASK-00/01/03/06 и проверки отказов |
| Модель данных | Сущности, связи и сохранность | Миграции/repositories, API-схемы, TASK-01–04/06 и проверки конкуренции/восстановления |
| План и задачи | Порядок работы, входы и критерии завершения | Ссылки зависимых задач, соответствие REQ/AC и фактический журнал проверок |
| Фактическое состояние репозитория и Pixso | Состав, стадия реализации, добавление/удаление кадров, подтверждённые проверки | Статус проекта, README, разделы состава/проверок описания макета и темы; прежние результаты оставлять в истории с явным уточнением |

При изменении общего правила сначала обновить его источник, затем все зависимые модули из таблицы. Численные пределы не задаются заново в задачах. TASK-00 → TASK-01 → TASK-02 → TASK-03 → TASK-04 → TASK-05 → TASK-06; полный список инструкций и их критерии доступны в плане.

Текущее состояние и пределы проверки: [статус проекта](docs/project-status.md). Порядок именования файлов и актуализации: [навигация docs](docs/README.md). Проверка переносимости документации: `python3 scripts/verify_docs.py`. Прежний подробный отчёт версии 0.2 хранится локально в `.local/spec-v02/verification.md` вне Git; сводки проверок находятся в [истории](docs/history/README.md).

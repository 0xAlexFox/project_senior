# Инструкции проекта project_senior

## Контекст

Проект содержит спецификацию web-конвертера, контракт API и документацию двух тем макета Pixso и начальную реализацию frontend: главную и форму входа. Backend и БД приложения ещё не реализованы. Порядок чтения и зависимости документов описаны в `README.md`; текущее состояние — в `docs/project-status.md`, имена файлов и ведение истории — в `docs/README.md`. Полное описание макета, визуальные токены, размеры и формулы — в `docs/mockup-specification.md`; `DESIGN.md` — только краткая точка входа. При изменении требований обновлять зависимые документы по его матрице.

## Текущая граница подготовки

24 ноября 2026 г. владелец разрешил начало frontend: базу стилей, компонентов и layout, главную страницу и следующую страницу входа, с явными заглушками недоступных данных и действий. Разрешены необходимые исходники web и настройки запуска/проверки. Backend, миграции БД, runner и остальные полноценные страницы не входят в эту итерацию; их реализацию начинать по следующему поручению. Существующие Python-инструменты сохраняются. Фактическая готовность окружения и команды — в `docs/project-setup.md`; TASK-00/01 ещё не завершены.

## Git

Автоматически применять `$git-commit` для Git-задач, перед правками и при завершении содержательной итерации. Сначала читать `~/.agents/skills/git-commit/SKILL.md` и проектный `docs/git-flow.md`. Если навык недоступен, сообщить конкретный путь и препятствие.

Работать в своей ветке, при параллельном изменении папки — в отдельном worktree. Сохранять чужие правки и staging. После крупных проверенных блоков создавать локальные атомарные коммиты и вести `docs/history/`. Перед готовым коммитом самостоятельно выполнять проверки по реальным изменениям. Для документации запускать `python3 scripts/verify_docs.py`, проверять согласованность и staged diff. Автопроверка не подтверждает существование кадров Pixso: их нужно сверять отдельно через редактор/MCP при изменении разделов состава и проверок макета. При изменении контракта проверять JSON и затронутые правила API. Команды приложения добавить после появления реализации.

После итоговой проверки остановиться на ревью с отчётом и вопросом по режиму изоляции. Merge, удаление worktree и создание PR требуют прямого текстового «Да, сливай» на представленный результат и соответствующие действия. Push и другие внешние операции требуют соответствующего разрешения задачи.

## Общение и данные

Общаться по-русски. Человекочитаемые даты оформлять по-русски в Europe/Moscow с точностью источника. Секреты, локальные данные и тяжёлые журналы сохранять вне Git по `.gitignore`. Субагентов запускать только по отдельному разрешению владельца.

## Памятка по итогам обучения и разработки

В этом проекте после каждой значимой темы автоматически актуализировать `заметки/подготовка-нового-web-проекта-с-codex.md` до итогового отчёта и коммита соответствующей итерации. Значимая тема — новое правило, освоенный инструмент, архитектурное решение, подход к дизайну, проверкам, безопасности или выпуску, а также разобранная нетривиальная ошибка, выводы из которых пригодятся при подготовке следующего web-проекта. Мелкая правка текста или каждый отдельный ответ не требуют новой записи.

Вносить сведения в подходящий раздел памятки: что делать, зачем и когда, как проверить результат, какие есть ограничения. При необходимости обновлять её чек-лист и стартовый промпт; поддерживать версию, дату и журнал изменений. Сохранять существующий материал, уточнять его вместо дублирования; большие справочные подробности оставлять в профильных документах со ссылкой. Проверенные решения отделять от предложений и непроверенных гипотез; не переносить секреты, личные данные и частные параметры текущего проекта как универсальные требования.

В журнале итерации и кратком итоговом отчёте указывать, какой раздел памятки дополнен. Если вывод уже полностью отражён, проверить актуальность и отметить существующий раздел без искусственной новой записи. Правило действует только в project_senior: не добавлять его автоматически в глобальные инструкции, навыки или инструкции будущих проектов.

## Проверка безопасности

Перед слиянием рабочей ветки в главную/защищённую применять `$project-security-review` из `~/.agents/skills/project-security-review/SKILL.md`: анализ кода и применимые проверки, локальный отчёт после финального коммита, `security_gate.py verify` для фактических source/target перед разрешённым merge. Следовать `docs/security-review.md`; BLOCKED и отсутствие обязательных результатов запрещают слияние. Скрипты и CI считать кодом, для отсутствующего приложения обосновывать N/A. Разрешение владельца на merge остаётся обязательным.
